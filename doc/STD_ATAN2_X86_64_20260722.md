# `PilotPhaseLock` phase detector: `fast_atan2f` vs `std::atan2` on x86_64

**Date:** 2026-07-22
**Subject:** speed of `PilotPhaseLock::process()`'s phase-detector `atan2`
(`sfmbase/PilotPhaseLock.cpp`)
**Branches compared:**

| branch | commit | phase-detector call |
|---|---|---|
| `dev` | `8cd9171` | `double phase_err = Utility::fast_atan2f(new_phasor_q, new_phasor_i);` (float table lookup) |
| `dev-std-atan2-pilot` | `afff274` | `double phase_err = std::atan2(new_phasor_q, new_phasor_i);` (double libm) |

`dev-std-atan2-pilot` is a **single commit** on top of `dev`; the only source
change is the one phase-detector line (plus its comment and includes). All
headers and `Filter.cpp` are identical between the two.

**Test host:** Intel Core i7-10710U (Comet Lake, x86_64), Ubuntu 26.04 LTS,
gcc 15.2.0, glibc 2.43, AVX2+FMA. CPU governor `powersave`, turbo enabled,
base 1.1 GHz / max 4.7 GHz. Build flags: the project's `OPTIMIZATION_FLAGS`
`-O3 -ftree-vectorize` with `-std=c++20` (no `-march=native`, no `-DNDEBUG`,
matching the real build). Measurements were CPU-pinned (`taskset -c 2`).

---

## Executive summary

* **On this x86_64 host, `std::atan2` (double) is `~2.2×` slower than
  `fast_atan2f` in the PLL's locked operating regime** — the *opposite* of the
  Apple M2 Pro / arm64 result reported in
  `doc/CORE_MATH_ATAN2F_20260722.md`, where `std::atan2` was `~1.6×` *faster*.
* Measured on the **real `PilotPhaseLock::process()`** compiled from each
  branch, the whole per-sample cost rises from **43.1 ns/sample (`dev`) to
  51.8 ns/sample (`dev-std-atan2-pilot`)** — **+8.7 ns/sample, ≈ +20 %.**
* That +8.7 ns/sample matches the isolated phase-detector delta almost exactly
  (`std::atan2` 15.64 ns − `fast_atan2f` 7.12 ns = 8.51 ns/call), confirming the
  slowdown is entirely the `atan2` change and nothing else.
* **`-march=native` does not change the verdict.** Adding it (gcc selects
  `-march=skylake` on this CPU) speeds the whole loop by `~5 %` for *both*
  branches, but the branch-to-branch gap stays at **≈ +21 %** and `std::atan2`
  stays `~2×` slower per call — the `~5 %` gain comes from vectorizing the
  surrounding arithmetic, not the phase detector (see §3.1).
* **The commit message on `dev-std-atan2-pilot` — "on modern FPUs `std::atan2`
  is faster than the `fast_atan2f()` float table lookup" — is true on
  arm64/macOS but false on this x86_64/glibc target.** The table lookup still
  earns its name here.
* The change is a genuine accuracy upgrade (`std::atan2` is `~10` orders of
  magnitude more accurate, effectively correctly rounded on glibc here), but as
  established previously that accuracy is **five orders of magnitude below the
  PLL's own phase-noise floor** and produces no audible or measurable output
  difference. The two branches' tracked frequency and output checksum agree to
  ≈4 significant figures.
* **Absolute cost of the regression is small** — +3.3 ms of CPU per second of
  audio, ≈0.33 % of one core — but it is a regression, not an improvement, on
  x86_64.

**Recommendation for x86_64 targets:** keep `fast_atan2f` (i.e. `dev`) if CPU is
the priority; the table is `~2.2×` faster and the extra `std::atan2` accuracy
buys the loop nothing audible. Adopt `std::atan2` (`dev-std-atan2-pilot`) only
if the simpler double-precision code and the accuracy/no-narrowing cleanliness
are judged worth `~0.3 %` more core time. The right choice is **hardware
dependent**: on arm64 `std::atan2` is the faster *and* more accurate option; on
this x86_64/glibc host it is only the more accurate one.

## 1. What differs between the branches

`git diff dev..dev-std-atan2-pilot -- sfmbase/PilotPhaseLock.cpp` (the whole
diff):

```diff
-    // double phase_err = std::atan2(new_phasor_q, new_phasor_i);
-    // Use float atan2 for fast and light-weight phase detection.
-    double phase_err = Utility::fast_atan2f(new_phasor_q, new_phasor_i);
+    // Use double std::atan2 for the phase detector: both phasor inputs are
+    // already double, and on modern FPUs std::atan2 is faster than the
+    // fast_atan2f() float table lookup while being correctly rounded.
+    double phase_err = std::atan2(new_phasor_q, new_phasor_i);
```

The phase detector runs **once per IF sample** (`sample_rate_if = 384000` Hz),
converting the biquad-filtered I/Q phasor into a phase error. Both inputs are
already `double`; `fast_atan2f` narrows them to `float` and does a 257-entry
table lookup with linear interpolation, whereas `std::atan2` consumes the
doubles directly. In the **locked** state the operating point is
`x = new_phasor_i ≈ +0.104`, `|y| ≪ x`, `|phase_err|` rms ≈ 0.0024 rad — a thin,
well-conditioned slice of `atan2`'s domain (per `doc/PLL_ANALYSIS_20260722.md`).

## 2. Measurement method

Two harnesses, both built with `-O3 -ftree-vectorize -std=c++20`, run pinned to
one core (`taskset -c 2`):

* **`pll_bench.cpp` — the branch-to-branch measurement.** Each branch's *actual*
  `sfmbase/PilotPhaseLock.cpp` (extracted with `git show <branch>:...`) is
  compiled together with the shared `sfmbase/Filter.cpp` and a driver. The
  driver builds a 384000-sample block (= exactly 19000 pilot cycles, so the
  pilot phase is continuous when the block is fed repeatedly), a 0.1-amplitude
  19 kHz pilot plus small Gaussian noise; warms the PLL into the locked steady
  state; then times `process()` (best of 25 trials × 30 calls), reporting
  ns/sample. Output is checksummed to defeat dead-code elimination and to check
  the two branches agree.
* **`atan_bench.cpp` — isolating the phase detector.** The real
  `Utility::fast_atan2f` (from `include/Utility.h`), `std::atan2` (double), and
  `std::atan2f` (float baseline) over 2²⁰-point data sets, best of 40, with a
  `volatile` sink. Reference truth for accuracy is `atan2l` (80-bit long
  double). Two data sets:
  * **A — PLL locked regime:** `x ~ N(0.104, 0.01)` (clamped > 0),
    `y = x·tan(err)`, `err ~ N(0, 0.0024)` — the distribution the locked loop
    actually sees.
  * **B — full four-quadrant range:** `x, y ~ U(-1, 1)`.

## 3. Speed: full `process()` (the branch-to-branch answer)

Real `PilotPhaseLock::process()`, ns per IF sample, best of 25 trials, pinned:

| branch | phase detector | ns/sample | vs `dev` |
|---|---|---:|---:|
| `dev` (`8cd9171`) | `fast_atan2f` | **43.13** | 1.00× |
| `dev-std-atan2-pilot` (`afff274`) | `std::atan2` | **51.82** | **1.20× (slower)** |

Consistency across 5 pinned passes was within ±0.1 ns/sample for each branch
(`dev` 43.13–43.22, `std::atan2` 51.82–52.47). The gap is **+8.7 ns/sample,
≈ +20 %** for the complete phase-locked-loop step (which also does `sin`, `cos`,
`sqrt`, two biquads and the NCO recursion per sample — so `atan2` is ~20 % of
the whole loop, and swapping it moves the whole loop by ~20 %).

### 3.1 Effect of `-march=native`

The project's default `OPTIMIZATION_FLAGS` do **not** pass `-march`. Re-running
the same pinned benchmarks with `-O3 -ftree-vectorize -march=native` added — gcc
selects `-march=skylake -mtune=skylake` on this Comet Lake CPU — gives, in the
same session:

| build | `dev` (`fast_atan2f`) | `dev-std-atan2-pilot` (`std::atan2`) | gap |
|---|---:|---:|---:|
| baseline (`-O3 -ftree-vectorize`) | 43.3 | 52.3 | +21 % |
| `+ -march=native` (skylake) | 40.9 | 49.6 | +21 % |

Isolated atan2, locked regime (A), ns/call:

| build | `fast_atan2f` | `std::atan2` | ratio |
|---|---:|---:|---:|
| baseline | 7.13 | 15.64 | 2.20× |
| `+ -march=native` | 7.47 | 15.52 | 2.08× |

`-march=native` shaves **≈ 5 % off the whole `process()` loop for both
branches**, but **the atan2 verdict is unchanged**: `std::atan2` stays `~2×`
slower per call and the branch-to-branch gap holds at **≈ +21 %**. The `~5 %`
gain comes entirely from AVX2/FMA vectorizing the surrounding biquads, `sin`,
`cos` and `sqrt` — *not* the phase detector. The isolated atan2 functions barely
move: `std::atan2` is glibc's precompiled library routine (never recompiled with
the project's flags), and `fast_atan2f` is a branchy scalar table lookup that
does not vectorize (it even came out marginally slower here, within noise). So
`-march=native` does not rescue `std::atan2` on x86_64; `fast_atan2f` remains
faster by the same margin.

## 4. Speed: isolated `atan2` backends

ns/call, best of 40, pinned:

| data set | function | ns/call | vs `fast_atan2f` |
|---|---|---:|---:|
| **A — PLL locked** | `fast_atan2f` | **7.12** | 1.00× |
| | `std::atan2` (double) | **15.64** | **2.20× (slower)** |
| | `atan2f` (float) | 14.96 | 2.10× (slower) |
| **B — full range** | `fast_atan2f` | 13.52 | 1.00× |
| | `std::atan2` (double) | 24.34 | 1.80× (slower) |
| | `atan2f` (float) | 14.94 | 1.11× (slower) |

* In the locked regime (A), `std::atan2` costs **+8.51 ns/call** over the table
  — which reproduces the +8.7 ns/sample seen in the full `process()` above,
  confirming the `atan2` line is the sole cause.
* On glibc here, **double `std::atan2` and float `atan2f` cost essentially the
  same** (15.6 vs 15.0 ns in A); glibc does not give the float entry point a
  speed advantage, so the table's win comes from being a branch-predicted table
  lookup, not from single precision.
* `fast_atan2f` is data-dependent and branchy: its quadrant/branch decisions
  predict perfectly in the locked regime (7.12 ns) but mispredict on random
  full-range data (13.52 ns). Even so it stays fastest in both regimes here.

## 5. Accuracy and output equivalence

Absolute error vs `atan2l`, radians:

| data set | function | max abs | rms | mean abs |
|---|---|---:|---:|---:|
| **A — PLL locked** | `fast_atan2f` | 4.11×10⁻⁸ | 6.98×10⁻⁹ | 4.11×10⁻⁹ |
| | **`std::atan2`** | **8.65×10⁻¹⁹** | 1.13×10⁻¹⁹ | 7.67×10⁻²⁰ |
| | `atan2f` | 1.17×10⁻⁹ | 1.00×10⁻¹⁰ | 6.46×10⁻¹¹ |
| **B — full range** | `fast_atan2f` | 1.53×10⁻⁶ | 7.64×10⁻⁷ | 6.63×10⁻⁷ |
| | **`std::atan2`** | **2.23×10⁻¹⁶** | 8.77×10⁻¹⁷ | 6.50×10⁻¹⁷ |
| | `atan2f` | 1.72×10⁻⁷ | 4.89×10⁻⁸ | 3.68×10⁻⁸ |

`std::atan2` on glibc 2.43 is at the machine-epsilon floor (effectively
correctly rounded here), `~10` orders of magnitude more accurate than the float
table. But the loop's own phase-error rms is **0.0024 rad**
(`doc/PLL_ANALYSIS_20260722.md`) — the table's 4×10⁻⁸ rad locked-regime error is
already `~5×10⁴` below that floor, so the extra accuracy cannot reach the output.

Output equivalence from the two real `process()` builds (same input, locked):

```
                     dev (fast_atan2f)     dev-std-atan2-pilot (std::atan2)
output checksum      0.000724674694        0.000722010759
freq_err             -7.39686398e-10       -7.39630915e-10
```

The tracked frequency error agrees to ~4 significant figures; the difference is
far below the loop's ±0.044 Hz jitter. **The two branches are audibly and
measurably identical at the output.**

## 6. Cross-platform contrast with the arm64 result

`doc/CORE_MATH_ATAN2F_20260722.md` measured the same functions on Apple M2 Pro
(arm64, macOS, Homebrew clang). Locked-regime ns/call, side by side:

| function | arm64 (M2 Pro) | x86_64 (i7-10710U) |
|---|---:|---:|
| `fast_atan2f` | 7.38 | 7.12 |
| `std::atan2` (double) | **4.56 (faster)** | **15.64 (slower)** |
| `atan2f` (float) | 2.04 | 14.96 |

The `fast_atan2f` table costs almost the same on both machines (~7 ns), but the
**system libm `atan2` differs by `~3.4×` between the two platforms** (4.56 ns on
Apple's libm vs 15.64 ns on glibc). On arm64 the hardware/libm makes `std::atan2`
the faster *and* more accurate choice; on this x86_64/glibc host it is only the
more accurate one. This is exactly the caveat the arm64 document raised:

> The ns/call figures are hardware-specific; the *ordering* … should be
> re-measured on the actual deployment target before acting on the speed
> argument.

This report is that re-measurement, and it **inverts the speed ordering** for
x86_64/glibc.

## 7. Cost in context and recommendation

**Absolute cost of the regression.** One `atan2` per 384 kHz sample ×
+8.7 ns/call = **+3.34 ms of CPU per second of audio ≈ 0.33 % of one core.**
The phase detector alone goes from ≈2.7 ms/s (`fast_atan2f`) to ≈6.0 ms/s
(`std::atan2`); the whole `process()` from ≈16.6 ms/s (1.7 % of a core) to
≈19.9 ms/s (2.0 % of a core). Small in absolute terms — this will not threaten
real-time decoding on this class of CPU — but it is a measurable slowdown with
no audible benefit.

**Decision matrix (this x86_64 target):**

| Goal | Choice | Why |
|---|---|---|
| Lowest CPU, accuracy irrelevant | **`dev` (`fast_atan2f`)** | `~2.2×` faster; table error is `~5×10⁴` below the loop's noise floor |
| Simpler double code, no float narrowing, correctly-rounded detector | `dev-std-atan2-pilot` (`std::atan2`) | cleaner and more accurate, at +0.33 % core |
| Bit-for-bit reproducible pilot phase across all libms/arches | neither — see `CORE_MATH_ATAN2F_20260722.md` (`cr_atan2`) | only CORE-MATH is correctly rounded *by construction* everywhere |

**Recommendation.** On x86_64/glibc, the speed argument for
`dev-std-atan2-pilot` does not hold: `std::atan2` is `~2.2×` slower than the
table and buys nothing the PLL can use. If this x86_64 host is the deployment
target and CPU matters, **keep `dev` (`fast_atan2f`)**. Merge
`dev-std-atan2-pilot` only for the code-cleanliness / accuracy reasons, and only
if the ~0.3 % extra core time is acceptable — and update the commit message,
since "std::atan2 is faster than the table on modern FPUs" is not true here.
Because the winner flips between arm64 and x86_64, a portable build that wants
the best of both could select the backend per architecture rather than commit to
one globally.

## 8. Reproduction

Harnesses live in the analysis scratchpad: `pll_bench.cpp` (real `process()`
driver), `atan_bench.cpp` (isolated backends + accuracy), `run.sh`.

```sh
REPO=/home/kenji/src/airspy-fmradion
INC="-I$REPO/include -I$REPO/build/_deps/fmt-src/include"
F="-Wall -std=c++20 -O3 -ftree-vectorize -DFMT_HEADER_ONLY"

git -C $REPO show dev:sfmbase/PilotPhaseLock.cpp                 > pll_dev.cpp
git -C $REPO show dev-std-atan2-pilot:sfmbase/PilotPhaseLock.cpp > pll_std.cpp

g++ $F $INC -DLABEL='"dev(fast)"'  pll_dev.cpp $REPO/sfmbase/Filter.cpp pll_bench.cpp -o pll_bench_dev -lvolk
g++ $F $INC -DLABEL='"std::atan2"' pll_std.cpp $REPO/sfmbase/Filter.cpp pll_bench.cpp -o pll_bench_std -lvolk
g++ $F $INC atan_bench.cpp -o atan_bench -lvolk

taskset -c 2 ./pll_bench_dev
taskset -c 2 ./pll_bench_std
taskset -c 2 ./atan_bench

# For §3.1, append -march=native to F and rebuild the three binaries:
#   F="$F -march=native"
```

Numbers above are from Intel Core i7-10710U / Ubuntu 26.04 / gcc 15.2.0 /
glibc 2.43, CPU-pinned. The ns figures are hardware- and libm-specific; the
portable conclusion is the **ordering**: on x86_64/glibc the `fast_atan2f` table
is faster than `std::atan2`, reversing the arm64/macOS result.
