# Summary of changes: 20260713-0 to 20260716-0

This document summarizes all changes between tag `20260713-0` and
commit `d350ab0` (released as `20260716-0`): 33 commits, 54 files
changed, +3665/−114 lines.

Unlike the previous release, this one does touch DSP-adjacent code
and the resampler configuration. It consists of four threads of
work: (a) reconfiguring the r8brain resamplers for explicit
low-latency filter parameters, including a fix for a build-system
define-propagation bug that had silently determined the shipped
filter design all along; (b) a set of measured latency-analysis
documents for FM, AM, CW, and NBFM reception; (c) a macOS-specific
low-latency PortAudio experiment that was tried, measured, and then
generalized away in favor of a portable `-L`/`--portaudio-latency`
command-line option with one 40 ms floor on all platforms; and (d)
changing the audio-path `Sample` type alias in `include/SoftFM.h`
from `double` to `float`, the headline change of the release, with
the pilot PLL's recursive state deliberately kept in `double` to
avoid reintroducing phase noise. Copyright years and the version
string were bumped to `20260716-0` in the final commit.

## 1. r8brain resampler low-latency reconfiguration

See [doc/LATENCY_PLAN_20260713.md](LATENCY_PLAN_20260713.md),
especially its executive summary and sections 7-10, for the full
measured analysis.

`r8b::CDSPResampler` (used by both `AudioResampler` and
`IfResampler`) previously ran with library-default filter design
parameters (`ReqTransBand`/`ReqAtten`) tuned for mastering-grade
conversion, which cost far more group delay than an FM/AM broadcast
signal needs. `c33e03d` gives both resamplers explicit,
signal-appropriate parameters:

- `AudioResampler` (`include/AudioResampler.h`): `req_trans_band =
  15.0`, `req_atten = 120.0` — a 20.4 kHz passband edge (above the
  19 kHz pilot, which is removed downstream by the pilot-cut FIR
  anyway) and 120 dB stop-band attenuation, well above FM broadcast
  SNR.
- `IfResampler` (`include/IfResampler.h`): `req_trans_band = 10.0`,
  `req_atten = 140.0` — a 172.8 kHz passband edge at the 384 kHz IF
  rate, far beyond the FM channel bandwidth. This also required
  switching `IfResampler::m_cdspr_re`/`m_cdspr_im` from the fixed
  `r8b::CDSPResampler24` preset to the parameterized
  `r8b::CDSPResampler` class, since `CDSPResampler24` does not accept
  explicit design parameters.

The first commit's comments quoted 77.1 ms → 4.8 ms (audio) and
13.3 ms → 1.6 ms (IF) group-delay reductions, measured with
`R8B_EXTFFT`/`R8B_FASTTIMING`/`R8B_PFFFT_DOUBLE` defined. `08a5932`
corrects these: those defines were never actually compiled into the
resampler code that ships (see below), so the as-built group delays
are roughly half what the probe measured — 34.4 ms → 2.1 ms (audio)
and 6.2 ms → 0.7 ms (IF). Section 9 of the doc cross-validates this
against an end-to-end 6-second synthetic-FM decode: the resampler
chain's real-time deficit drops from 40.58 ms to 2.85 ms (measured
both from WAV duration and from `getInLenBeforeOutStart()` debug
instrumentation), with the tone-onset position in the output
identical between builds — confirming the change alters latency only,
not content alignment or decoded audio.

The root cause behind the correction is itself a build defect, fixed
in `c64d26e`: `CMakeLists.txt` built a `r8b` library target from
`r8brain-free-src/fft/pffft_double.c` with `PUBLIC` compile
definitions `R8B_EXTFFT=1 R8B_FASTTIMING=1 R8B_PFFFT_DOUBLE=1`, but
only `main.cpp`/`airspy-fmradion` linked that target — `sfmbase`,
where `AudioResampler.cpp` and `IfResampler.cpp` actually instantiate
r8brain's header-only templates, never linked `r8b` and so never saw
the defines. This meant (1) the shipped binary always ran r8brain's
default no-defines code path regardless of the target's defines, (2)
`pffft_double.c` was compiled but never referenced, so the object was
dead weight, and (3) `main.cpp` and `sfmbase` compiled the same
r8brain header templates under two different sets of preprocessor
defines — an ODR hazard, since which definition the linker picked for
any inline code reachable from both was arbitrary. `c64d26e` removes
the `r8b` target and its defines entirely, standardizing the whole
program on the no-defines configuration it already ran; r8brain stays
available header-only via the existing include path. Verified
bit-identical decode output and unchanged as-built resampler sample
counts (`IfResampler` 858, `AudioResampler` 809 input samples) before
and after.

User-visible effect: for FM reception, resampler-chain latency drops
by about 37.7 ms measured end-to-end, with no change to decoded
audio content, at the cost of two `static constexpr` parameter pairs
and one fewer CMake library target.

## 3. macOS PortAudio latency experiment, generalized into `-L`/`--portaudio-latency`

This theme has three stages: try a macOS-specific fix, measure it,
then replace it with a portable option once the measurement showed
the macOS-specific mechanism itself contributed little.

**Stage 1 (tried and later removed).** `ec48dd6` added an
`#ifdef __APPLE__` branch to `PortAudioOutput`'s constructor
(`sfmbase/AudioOutput.cpp`) requesting the device's
`defaultLowOutputLatency` (floored at a new `minimum_latency_low =
0.025`) instead of `defaultHighOutputLatency` (floored at
`minimum_latency_default = 0.04`), plus a CoreAudio
`paMacCoreChangeDeviceParameters` stream-info flag via
`pa_mac_core.h`. `cde04d0` removed the `paMacCoreChangeDeviceParameters`
flag one commit later: it measured no latency improvement.
Section 11 of `LATENCY_PLAN_20260713.md` (added by `3bcb496`) measured
the remaining `defaultLowOutputLatency` change on a FiiO K7 USB DAC:
PortAudio-granted output latency dropped from 210.7 ms to 110.3 ms,
entirely attributable to the smaller latency *request* — CoreAudio
grants roughly 5x whatever `suggestedLatency` is requested on this
device, so the 40 ms → 25 ms floor drop was the whole effect, not the
CoreAudio flag.

**Stage 2 (the generalization).** `1196d95` added a new `-L`
(`--portaudio-latency`) command-line option: a float in `[1, 40]` ms,
range-checked in `main.cpp` with the existing `badarg()` convention,
converted to seconds (`PaTime`) and passed as a new fourth,
defaulted `PortAudioOutput` constructor parameter
(`suggested_latency_sec = -1.0`, where negative means "unset"). When
given, the value is used verbatim as `suggestedLatency`, bypassing
the floor logic entirely; `-L` is parsed and range-checked
unconditionally (matching precedent for other output-specific
options) but has effect only under PortAudio output (`-P`).
`a4cf5ca` and `d3683db` then removed the macOS-specific
`defaultLowOutputLatency`/`minimum_latency_low` branch from stage 1
altogether, unifying every platform on
`defaultHighOutputLatency`/`minimum_latency_default` (40 ms) as the
one no-option-given default; `f0aa495` and `cc3489f` are documentation
follow-ups fixing a dangling comment and rewording the default-latency
description in `usage()`, `README.md`, and `CHANGES.md` from
"platform-dependent" to "floored at 40 milliseconds" to match. See
[doc/LATENCY_OPTION_20260715.md](LATENCY_OPTION_20260715.md)
(`ac312a5`) for the full branch-level diff and interface-compatibility
analysis (the constructor change is purely additive; existing
3-argument call sites remain valid).

Net effect: the macOS-only code path and its two `minimum_latency_*`
constants are both gone from the codebase as of `d350ab0`. The only
remaining latency control is the portable `-L` option, defaulting to
a 40 ms floor identical on macOS, Linux, and Raspberry Pi OS, with an
explicit `-L` value able to request as low as 1 ms (subject to what
the platform's PortAudio backend actually grants).

**A note on `CHANGES.md`.** The `dev-resampler-lowlatency 20260714`
entry in `CHANGES.md` (added by `9ff8a16`, *before* the stage-2
commits above) still describes the removed stage-1 mechanism
("PortAudioOutput now requests `defaultLowOutputLatency` with a
25 ms minimum ... 210.7 -> 110.3 ms ... Net measured steady-state
latency reduction: ~138 ms for FM, ~144 ms for AM/CW/NBFM") and was
not revised after `a4cf5ca`/`d3683db` deleted that code path in favor
of `-L`. As of `d350ab0` this changelog entry documents a mechanism
that no longer exists in the source; the `20260716-0` entry above it
and the `-L`-focused `dev-portaudio-latency-option 20260715` entry
are accurate. The entry has since been corrected (after `d350ab0`)
to note that the macOS-specific path was measured, removed, and
superseded by `-L`.

## 4. `Sample` type change from `double` to `float`

The headline DSP-adjacent change of the release (`06b0d5d`), backed
by [doc/FLOAT_OUTPUT_20260716.md](FLOAT_OUTPUT_20260716.md)
(`b428322`), which documents a two-round evaluation process.

`include/SoftFM.h` changes `using Sample = double;` to `using Sample
= float;`; `SampleVector` and the FIR coefficient type used in
`FilterParameters.cpp` track the alias change automatically. This
halves the memory footprint and memory bandwidth of every
`Sample`-typed buffer in the audio path (post-discriminator baseband,
stereo demod, resampler output, file/PortAudio output buffers).

The evaluation's round 1 (fully float, including `PilotPhaseLock`'s
internal state) measured a −82.3 dBFS difference against the
all-double baseline, entirely concentrated in the stereo (L−R)
channel — the signature of a slightly different, still-valid 38 kHz
PLL phase trajectory, since `PilotPhaseLock::m_phase`/`m_freq` are
live recursive accumulators where one float ULP at the pilot's phase
increment is large enough to matter. The final proposal (round 2,
what was actually committed) keeps this state in explicit `double`
purely by widening the types, at zero measured CPU cost (the PLL
state is O(1) per decoder instance, not per-sample bulk data):

- `include/PilotPhaseLock.h`: `m_minfreq`, `m_maxfreq`, `m_freq`,
  `m_phase`, `m_pilot_level`, and `m_freq_err` are now `double`
  instead of `Sample`.
- `sfmbase/PilotPhaseLock.cpp`: every per-sample local feeding the
  recursion inside `process()` (`psin`, `pcos`, `x`, `phasor_i/q`,
  `new_phasor_i/q`, `phase_err`, `new_phase_err`) is likewise typed
  `double`; only the final `samples_out[i]` write narrows back to
  `Sample`.

All the other recursive IIR filters in `include/Filter.h`
(`FirstOrderIirFilter`, `BiquadIirFilter` — covering de-emphasis, the
4.8 Hz DC-blocking high-pass, and the pilot PLL's own loop filter)
already hardcoded `double` coefficients and state independent of the
`Sample` typedef, so they needed no change; the `Sample` switch only
narrows their per-sample I/O boundaries, not their recursions.

Downstream, several call sites that were doing real `double`↔`float`
conversion became same-type no-ops and were simplified or adapted:

- `sfmbase/FmDecode.cpp`, `sfmbase/NbfmDecode.cpp`,
  `sfmbase/AmDecode.cpp`: `volk_32f_convert_64f` (copying the
  discriminator's `float`-typed `IQSampleDecodedVector` into the
  `SampleVector` baseband buffer) degenerates to a same-type copy
  once `Sample` is `float`; replaced with `std::copy_n`.
- `FmDecoder::demod_stereo` (`sfmbase/FmDecode.cpp`):
  `volk_64f_x2_multiply_64f` → `volk_32f_x2_multiply_32f`.
- `sfmbase/AudioOutput.cpp`: `SndfileOutput::write` uses
  `sf_write_float` instead of `sf_write_double` (libsndfile handles
  the on-disk format scaling internally either way);
  `PortAudioOutput::write`'s `volk_64f_convert_32f` into `m_floatbuf`
  becomes a same-type `std::copy_n`.
- `sfmbase/AudioResampler.cpp`: r8brain's `CDSPResampler::process`
  is double-only, so the previous direct `const_cast<double
  *>(samples_in.data())` no longer type-checks. The input is now
  widened into a new `DoubleVector` (`include/SoftFM.h`:
  `using DoubleVector = std::vector<double>;`) via `std::copy_n`, and
  the resampler's `double *` output is narrowed back into `Sample`
  element-by-element on the way out — mirroring the pattern
  `sfmbase/IfResampler.cpp` already used for its (unrelated, IQ-typed)
  double-only r8brain instances.
- `main.cpp`: the audio-level measurement's
  `audiosamples_float`/`volk_64f_convert_32f` conversion buffer is
  removed; `Utility::samples_mean_rms` is called directly on the
  now-`float` `audiosamples`.

Verification used a 20-second off-the-air 82.5 MHz piano broadcast
recording (Airspy HF+, 384 kHz IQ) decoded by both the double
baseline and the final float build to float32 WAV. Against the
double pipeline: −140.2 dBFS RMS difference overall (SNR 120.1 dB),
flat across the whole recording (no error accumulation); mid (L+R)
SNR 118.5 dB, side (L−R) SNR 134.2 dB; audible-band (0–18.5 kHz)
per-band power identical to ±0.000 dB. The only measurable spectral
change is in the pilot-cut filter's stopband (≥18.5 kHz), where
residual energy rises from about −180 dBFS to about −152 dBFS — the
float-precision floor of the `Sample`-typed 127-tap pilot-cut FIR
accumulator, still roughly 56 dB below 16-bit quantization and below
one 24-bit LSB. Decode CPU time for the same file dropped from 1.48 s
to 1.24 s of user time, about 16% less, with the double-pinned PLL
state costing nothing measurable relative to the fully-float round-1
variant (1.27 s). Output is deterministic (byte-identical across
repeated runs of the same binary). AM and NBFM paths compile and were
included in the conversion, but were not independently measured with
a live recording; their recursive filters are the same
double-protected `Filter.h` classes used by FM.
