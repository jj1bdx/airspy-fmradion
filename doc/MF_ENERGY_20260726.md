# Multipath filter coefficient energy on a real signal (2026-07-26)

What the adaptive multipath filter actually converges to on a recorded
off-air FM signal with real multipath, measured through the `COEFF_MONITOR`
compile-time flag (`main.cpp:53`). The subject is
`test-files/interfm-20260724102822z-iq.wav` — 384 kHz baseband IQ, the same
recording used as the dispersive-channel case in
`doc/LPF_VOLK_20260725.md` §3 — decoded with `-E36`.

## Executive summary

- **The filter is doing substantial work here.** Total off-reference
  coefficient energy settles at **−3.4 dB** relative to the pinned reference
  tap. This is not a near-identity filter (§3).
- **The reference tap stays exactly `(1+0j)`** in all 38 dumps, confirming the
  pin at `MultipathFilter.cpp:214` (§3).
- **The echo structure is short and post-cursor.** 87.6 % of the
  off-reference energy is on the post-cursor side, and 84 % of it lies within
  ±21 µs of the reference. The strongest taps are at +2.6, +7.8, +10.4 and
  +5.2 µs, all between −10 and −14 dB (§3, §4).
- **`-E36` is much longer than this channel needs.** The 82 taps beyond
  ±83 µs hold 0.25 % of the off-reference energy between them; roughly
  `-E8`–`-E12` would span ~99 % of what is measured. This is the situation the
  constructor comment warns about — taps beyond the delay spread carry no
  signal and add gradient noise. It is *not* by itself a recommendation to
  change the default (§4).
- **`COEFF_MONITOR` was silenced by `-q`.** The `#ifdef` block sat inside the
  `if (!quietmode)` status-display branch, so the normal way to run a file
  decode produced no dumps at all. Fixed by moving the block out of that
  branch (§6).

## 1. Method

Build with the flag defined, without touching the working tree:

```sh
cmake -S . -B build-coeff -DEXTRA_FLAGS="-DCOEFF_MONITOR=1 -DDEBUG_MULTIPATH_FILTER=1"
cmake --build build-coeff --target all
```

Decode 40 s of the recording (`filesource` paces itself to real time):

```sh
./build-coeff/airspy-fmradion -t filesource \
  -c freq=82000000,srate=384000,filename=test-files/interfm-20260724102822z-iq.wav \
  -E36 -G /dev/null 2> coeff.log
```

The monitor emits one CSV line every `stat_rate * 10` = 200 blocks — about one
dump per second at this block rate — carrying the block number, the current
CMA error, and all 145 taps as `i,re,im` triples:

```
block,7400,mf_error,-0.026705503,mf_coeff,0,0.000000000,0.000000000,1,...
```

40 s produced 38 dumps, blocks 0 through 7400. Note the absence of `-q` in the
command above; see §6.

## 2. Index-to-delay mapping

With `stages = 36`: `m_filter_order` = 145, `m_index_reference_point` = 109.
The dot product in `single_process()` pairs `m_coeff[i]` with `m_window[i]`,
where `m_window[0]` is the *oldest* sample in the window. So a tap **below**
the reference index multiplies a more-delayed input, and therefore corrects an
echo arriving **after** the direct path (post-cursor); a tap above the
reference index is pre-cursor. Tap spacing is one IF sample,
1/384000 s = **2.604 µs**.

| index range | count | delay relative to reference |
|---|---|---|
| 0 … 108 | 109 | post-cursor, +283.8 … +2.6 µs |
| 109 | 1 | reference, pinned to `(1+0j)` |
| 110 … 144 | 35 | pre-cursor, −2.6 … −91.1 µs |

That is the 3:1 post/pre split the constructor comment describes. Note in
passing that the comment on `initialize_coefficients()` states the mapping as
`[-(stages * 3) … 0 … +stages]`, i.e. −108 … +36, while the arithmetic above
gives −109 … +35; the reference index is `stages * 3 + 1`, not `stages * 3`.
The one-tap discrepancy is in the comment only and is not touched here.

## 3. What the filter converged to

Averaged over the last 10 dumps (blocks 5600–7400):

**Off-reference energy: −3.4 dB** relative to the reference tap. The
reference tap reads exactly `(1+0j)` in every dump.

Strongest taps, last dump (block 7400):

| tap | delay | \|c\| | dB | phase |
|---|---|---|---|---|
| 108 | +2.60 µs | 0.306 | −10.3 | +27° |
| 106 | +7.81 µs | 0.276 | −11.2 | +169° |
| 105 | +10.42 µs | 0.227 | −12.9 | −175° |
| 107 | +5.21 µs | 0.212 | −13.5 | +121° |
| 110 | −2.60 µs (pre-cursor) | 0.202 | −13.9 | −52° |
| 102 | +18.23 µs | 0.177 | −15.0 | −12° |

The pattern is stable: the same six taps lead at block 3800, with magnitudes
within ~7 % of these and phases within ~3°. The channel this recording
captures is therefore not drifting fast on the scale of tens of seconds, even
though individual taps fluctuate.

**Post-cursor 87.6 %, pre-cursor 12.4 %** of the off-reference energy — the
physically expected split, since real echoes arrive after the direct path and
pre-cursor taps mainly compensate the filter's own response.

## 4. Delay-spread profile

Mean tap power over the last 10 dumps, binned by absolute delay from the
reference and expressed as a share of total off-reference energy:

| window | share | taps in window |
|---|---|---|
| 0 – 10.4 µs | 57.2 % | 6 |
| 10.4 – 20.8 µs | 26.9 % | 8 |
| 20.8 – 41.7 µs | 12.2 % | 16 |
| 41.7 – 83.3 µs | 3.6 % | 32 |
| 83.3 – 166.7 µs | 0.22 % | 36 |
| 166.7 – 333 µs | 0.03 % | 46 |

84 % of the correction lives in the 14 taps within ±21 µs. The 82 taps beyond
±83 µs hold a quarter of one percent between them, which at this level is
indistinguishable from adaptation noise on taps that have no echo to lock to.

The constructor comment states the design intent directly: *"Size this to the
echo delay spread; more stages is not safer. Each stage adds 4 taps spanning
10.4 us … Taps beyond the delay spread carry no signal and add gradient noise,
which raises the residual error and costs CPU."* This measurement is a
concrete instance of that: on this recording `-E36` spends roughly two-thirds
of its taps on delays where nothing is arriving.

**What this does not establish.** It does not follow that a shorter filter
sounds better here, and this measurement cannot settle that:

- `doc/MULTIPATH_FILTER_DESIGN_20260724.md` §17.4 records that the CM error is
  a poor proxy for audio quality **in both directions**, so neither `mf_error`
  nor tap energy can stand in for a listening test.
- The same document's field verdict is that the filter is a net loss on fading
  channels either way, which is a stronger constraint on how much weight to
  put on any tap-length tuning derived from one recording.
- One recording is one channel. The delay spread here is short; a different
  site or a different band could easily need the long tail that is idle in
  this file.

The honest reading is: the *shape* of the tap energy is what the design
predicts, and if a shorter default is ever considered, this profile is
evidence about where the useful taps are — not evidence that shortening
improves the audio.

## 5. CMA error

`mf_error` stays within ±0.03 of zero across the whole run (target level 1.0),
with a single −0.090 excursion at block 6400 that is gone by the next dump —
consistent with a fade the loop recovered from. No divergence: the
`divergence_limit` checks in `process()` never fired, and the decode ran to
the end of the 40 s window.

## 6. `COEFF_MONITOR` was suppressed by `-q`

The first run of this measurement used `-E36 -q`, the usual form for a file
decode, and produced **zero** dumps. The `#ifdef COEFF_MONITOR` block was
nested inside the `if (!quietmode)` branch that guards the per-block status
display, so quiet mode silenced the debug dump along with the status line.

Nothing about a coefficient dump belongs to the status display: it has its own
`block % (stat_rate * 10)` cadence, its own `modtype`/`multipathfilter_stages`
guards, and it writes complete lines rather than the `\r`-updated status
field. The block has been moved out of `if (!quietmode)` so the monitor works
regardless of `-q`, which also removes the interleaving of CSV lines with the
`\r`-rewritten status line when quiet mode is off.

## 7. Reproduction

Parsing script for the log (the numbers in §3 and §4 come from this):

```python
import re, math
txt = open("coeff.log", errors="replace").read()
recs = []
for m in re.finditer(
        r'block,(\d+),mf_error,(-?[\d.]+),mf_coeff,((?:\d+,-?[\d.]+,-?[\d.]+,)+)', txt):
    f = m.group(3).rstrip(',').split(',')
    recs.append((int(m.group(1)), float(m.group(2)),
                 [complex(float(f[i+1]), float(f[i+2])) for i in range(0, len(f), 3)]))

REF, TS = 109, 1e6 / 384000.0          # reference index, tap spacing in us
avg = [0.0] * 145
for _, _, c in recs[-10:]:
    for i, v in enumerate(c):
        avg[i] += abs(v) ** 2 / 10
tot = sum(avg) - avg[REF]
print("off-reference energy: %+.1f dB" % (10 * math.log10(tot)))
for lo, hi in [(0, 4), (4, 8), (8, 16), (16, 32), (32, 64), (64, 128)]:
    e = sum(avg[i] for i in range(145)
            if i != REF and lo <= abs(i - REF) < hi)
    print("  %5.1f-%6.1f us: %6.2f %%" % (lo * TS, hi * TS, 100 * e / tot))
```

Delay of tap `i` is `(REF - i) * 2.604 µs`, positive being post-cursor.
